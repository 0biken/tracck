Tracck design system

Rules, tokens, and components for building Tracck screens. Tracck turns what people have already shipped into resumes they can trust, so the interface is built around one idea: every claim shows where it came from.

Version 1.0, October 12, 2026. Tokens, component rules, and the conformance checklist are normative. Screenshots and sample copy are illustrative. Status names match the enums in the Technical Architecture, Revision 2.

Principles

Five rules that settle most design arguments. Each one comes from a requirement in the architecture.

  1. Show where it came from. Every claim carries its source and the passage that supports it, highlighted. A user should never wonder why a bullet is on their resume.
  2. Never fake certainty. Imported, suggested, and confirmed entries look different. A number we cannot find in a source is flagged for the user, not polished into the draft.
  3. Long work is calm work. Imports and builds run in the background. Show the real step from the server, say the user can leave, and email them when it is done. No fake progress bars.
  4. Say what is missing. Partial imports, unavailable sources, and gaps against a job description are stated plainly, with a next step.
  5. Stay light on data. Built for a 360px phone on a slow or metered connection: two web fonts, no required animation, skeletons for loading, small payloads.

Voice of the visual language

Think of a document under review: dark ink on paper, a ballpoint pen for the one thing you should do next, and a highlighter for the passage that proves a point. Ink and paper carry almost everything. The pen marks the primary action and links. The highlighter is reserved for source excerpts, so when someone sees yellow they know it means evidence.

Rules

  • Ink and paper carry about nine tenths of any screen. Use Ballpoint for the single primary action in a view, for links, and for the focus ring.
  • Highlighter marks source excerpts that support a claim. It is never a button, a banner, or decoration.
  • Status colors express status only. Pair every status color with an icon and a text label, so nothing relies on color alone.
  • Rejected entries are neutral, not red. Rejecting is a decision the user made, not an error.
  • No gradients as decoration, and no raw hex values in components. Reference tokens.

Rules

  • Sentence case everywhere. No all-caps labels and no tracked-out eyebrows.
  • Keep prose to 60 to 70 characters per line. Cards and dialogs set their own max width.
  • Form inputs are 16px so mobile browsers do not zoom on focus.
  • Use tabular numerals (font-variant-numeric: tabular-nums) in tables and anywhere numbers line up.
  • Load only Bricolage Grotesque 600 and 700 and Instrument Sans 400, 500, and 600, with font-display: swap. Fallback stacks are system fonts.

  • Inside controls: 8 to 16px. Between related items: 8 to 12px. Between groups in a card: 16 to 24px. Between page sections: 32 to 48px.

Motion

Motion answers an action or reports a change. There are no entrance animations, and nothing moves just to catch attention.

TokenDurationUse
instant90msPress feedback
fast140msHover, focus, color changes
base220msDisclosure, progress, toast in and out

Easing is cubic-bezier(.2, 0, 0, 1). With prefers-reduced-motion, remove transitions and spinners rotate no more: state is still carried by the icon and label.

Icons and layering

  • Icons come from Lucide, drawn at a 1.75px stroke, sized 16px inline and 20px for standalone. Icons never carry meaning alone.
  • Z-index scale: base 0, sticky 10, menu 20, banner 30, overlay 40, dialog 50, toast 60.

Tokens

The code behind everything above. Components reference tokens, never hex values, so one change here updates every screen and both themes.

Components

Each component lists its variants, states, and rules. Every component must handle default, hover, focus, disabled, loading, and error where they apply, in both themes.

Button

One primary button per view. Labels are verbs that say exactly what happens, and they keep the same name through the whole flow: the Confirm button leads to a toast that says "Entry confirmed".

Sizes: small is for dense desktop areas only. Large is for the main call to action on a phone.

Segmented control

Switches between views of the same list, such as filtering the review queue. Use it for 2 to 4 options. It is not navigation.

Dialog

Used for short, focused tasks like pasting posts or fetching a portfolio. It opens centered at 1024px and up and as a full-height sheet below that. The title names the task, the primary action sits at the right of the footer, and Escape always closes it.

Toast

Confirms a user action that has no visible result elsewhere. It repeats the action's verb, stays for 6 seconds, pauses on hover and focus, and offers Undo for anything reversible. Never use a toast for an error the user must act on.

Patterns

How the components combine into the screens that matter most. Each pattern is drawn from the flows in the architecture.

The core review screen. Show the claim, its source, and the exact supporting passage. Offer Confirm, Edit, and Reject, and make each reversible. If a claim contains a number that no source supports, block confirmation until the user fixes it or removes the number.

    Onboarding

    This is a real sequence, so it is numbered. Users can leave and come back at any step, and no restricted integration is ever required.

    1. Explain and ask for consent. Say what Tracck will import and why, before anything is requested from a provider.
    2. Add sources. Connect, upload, or skip each one. A CV upload alone is enough to continue.
    3. Let it run in the background. Imports start immediately and progress is visible. The user can move on without waiting.
    4. Review what we found. Confirm, edit, or reject entries. Partial results are fine.
    5. Pick a role. Paste a job description or choose a general profile, then build.

    TypeArial, Calibri, or an equivalent standard font. Name 18 to 20pt bold, section headings 11 to 12pt bold, body 10 to 11pt. Black text on white.
    HeadingsStandard names that parsers expect: Summary, Experience, Projects, Skills, Education, Certifications. Reverse chronological order.
    CharactersPlain bullets and a hyphen in date ranges. No decorative symbols or special glyphs.
    LinksWritten out as visible text, not hidden behind labels.
    ContentEvery factual bullet traces to an entry in the record. Nothing appears on the page that the user has not confirmed.
    FormatsPDF and DOCX are rendered from the same structured content, so they never disagree.

    Content and voice

    Words are part of the interface. Write from the user's side, name things by what they mean to a person, and say exactly what will happen.

    Principles

    • Plain verbs, active voice, sentence case, no exclamation marks, no filler.
    • Say what happened, then what to do. Errors do not apologize and are never vague.
    • Keep one name for an action through the whole flow: Confirm entry, then "Entry confirmed".
    • Show numbers only when a source backs them. Prefer "3 of 4 required skills have evidence" to a made-up match score.
    • Do not promise outcomes. Say the resume is built to be readable by applicant tracking systems, not that it will pass them.
    • Describe states in time the user understands: "You can leave this page", not "Job enqueued".
    Write
    • Confirm entry
    • We could not read your CV. Upload a PDF or DOCX.
    • Verifying every claim has a source
    • Upload your LinkedIn data export
    Avoid
    • Submit
    • Oops! Something went wrong.
    • Processing…
    • Connect LinkedIn, when the connection cannot import what we promise

    Accessibility

    The target is WCAG 2.2 level AA. Most of it is built into the tokens and components, and the rest is enforced by the checklist.

    AreaRequirement
    ContrastText 4.5:1, large text and interface boundaries 3:1, in both themes. The contrast table in Color is the reference.
    KeyboardEverything works without a mouse, in a logical order. Focus is always visible: a 2px accent outline with a 2px offset.
    Target size24px is the minimum. Buttons and fields are 40px, and 44px on touch devices.
    Not by color aloneEvery status has an icon and text. Charts and meters carry a text label.
    Live updatesJob progress uses role="status" and announces step changes only. Failures that need action use role="alert". Server-sent events must not announce every update.
    DialogsFocus moves in, stays trapped, and returns to the trigger. Escape closes. Background content is inert.
    FormsVisible labels, errors linked with aria-describedby, a summary of errors at the top after a failed submit, and no placeholder-only labels.
    MotionRespect prefers-reduced-motion. Nothing essential depends on animation, and nothing flashes.
    Zoom and reflowUsable at 200% zoom and at 320px width without horizontal scrolling, apart from tables and code blocks.
    DocumentsThe resume preview is real text, not an image, and the exported PDF keeps a text layer.
    LanguageSet lang on the page and on any text in another language. Use plain wording; people read this interface in a second language, too.

    Patterns that fail review

    • A spinner that waits on a single request for generation or import.
    • A progress bar driven by a timer instead of server state.
    • An email provider, or any integration that cannot import data, shown in a list of sources.
    • A claim, number, or skill on a resume with no entry behind it.
    • A model confidence score shown as a percentage or as proof.
    • Hex values or arbitrary pixel values in components, or a dark: variant to patch over a missing token.
    • Status shown by color alone, or a dialog without focus management.
    • Gradients, glows, or entrance animations added for decoration.
